========================================================================
GUÍA DE INSTALACIÓN — GesmedWeb en un servidor nuevo (Ubuntu 26.04)
========================================================================
Última actualización: 2026-09-06 (fix del rollback destructivo del orquestador de migración y de errores puntuales en prescripcion/certificado)

Esta guía instala GesmedWeb desde cero en un servidor limpio, usando:
  - Dump de ESTRUCTURA (no create_all() de SQLModel) para regenerar el
    esquema de la base de datos, ya que mis_modelos.py todavía tiene
    diferencias cosméticas de tipo/nullable respecto a la BD real
    (ver migrations/verificar_estructura.py).
  - migrations/parametros_fijos.py para poblar los catálogos fijos.
  - migrations/crear_admin_inicial.py para crear el primer usuario ADMIN.

NOTA: la base de datos "geodata" (creada originalmente para separar el
perfil de usuarios) quedó en desuso al pasar a cifrado AES-256-GCM sobre
la tabla points de gesmed. No se crea ni se usa en esta guía. El código
muerto que la referenciaba (GesmedWeb/querys/points.py y la variable
_URL_GEODATA en querys.py) fue eliminado del proyecto.

------------------------------------------------------------------------
1. SISTEMA BASE
------------------------------------------------------------------------
sudo apt update && sudo apt upgrade -y
sudo apt install -y python3 python3-venv python3-pip git \
    mariadb-server mariadb-client build-essential \
    nodejs npm unzip curl

------------------------------------------------------------------------
2. MARIADB
------------------------------------------------------------------------
sudo mysql_secure_installation

sudo mysql -e "
  CREATE DATABASE gesmed CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
  CREATE USER 'med_admin'@'localhost' IDENTIFIED BY '<password-fuerte>';
  GRANT ALL PRIVILEGES ON gesmed.* TO 'med_admin'@'localhost';
  FLUSH PRIVILEGES;
"

Solo se necesita la base "gesmed". No se crea "geodata" (ver nota arriba).

------------------------------------------------------------------------
3. ESTRUCTURA DE LA BASE DE DATOS (dump de estructura, no create_all())
------------------------------------------------------------------------
Desde tu gesmed local (o el servidor de referencia), generar un dump
SOLO de estructura (sin datos de pacientes reales):

    mysqldump --no-data --routines --triggers \
      --ignore-table=gesmed.atencion_amaymed \
      --ignore-table=gesmed.atencion_amaymed_gesmed \
      --ignore-table=gesmed.diagnostico_amaymed \
      --ignore-table=gesmed.diagnostico_amaymed_gesmed \
      -h localhost -u med_admin -p gesmed > sql/gesmed_estructura.sql

IMPORTANTE — usar el binario real de "mysqldump" (CLI), NO el export
web de phpMyAdmin. El export de phpMyAdmin no incluye el wrapping
"SET FOREIGN_KEY_CHECKS=0/1" que mysqldump sí agrega automáticamente,
y sin eso la creación de tablas puede fallar según el orden en que
aparecen en el archivo, con un error como:

    ERROR 1005 (HY000): Can't create table `gesmed`.`<tabla>`
    (errno: 150 "Foreign key constraint is incorrectly formed")

Si "mysqldump" no está en el PATH (p.ej. en Mac con XAMPP), usar la
ruta completa al binario, por ejemplo:
"/Applications/XAMPP/xamppfiles/bin/mysqldump".

Los 4 "--ignore-table" excluyen vistas de comparación/depuración que
solo existen en el entorno de desarrollo (atencion_amaymed,
atencion_amaymed_gesmed, diagnostico_amaymed, diagnostico_amaymed_gesmed),
usadas históricamente para comparar registros entre amaymed y gesmed
durante la migración. Estas vistas consultan directamente la base
"amaymed", y si se incluyen en el dump, la instalación falla en un
servidor donde amaymed no existe o no es accesible con un error como:

    ERROR 1142 (42000): ANY command denied to user 'med_admin'@'localhost'
    for table `amaymed`.`atencion`

El artefacto de instalación (gesmed_estructura.sql) NO debe contener
ninguna referencia a "amaymed" — puedes confirmarlo con:

    grep -i amaymed sql/gesmed_estructura.sql   # no debe imprimir nada

(Las vistas siguen existiendo normalmente en tu gesmed local de
desarrollo; solo se excluyen de este dump de instalación.)

Importante: sql/gesmed.sql (el dump completo actual del repo) NO sirve
para esto tal cual — contiene datos reales de pacientes (paciente,
atencion, diagnostico, etc.), no es un artefacto de instalación limpio.
Generar gesmed_estructura.sql como se indica arriba y usar ESE archivo
como el artefacto oficial de instalación (guardarlo en el repo junto a
parametros_fijos.sql).

Copiar el archivo al servidor nuevo y aplicarlo:

    mysql -u med_admin -p gesmed < sql/gesmed_estructura.sql

Si una aplicación anterior falló a mitad de camino (BD con tablas a
medias) y hay que reintentar, es más seguro recrear la BD vacía antes
de reaplicar el dump corregido:

    sudo mysql -e "
      DROP DATABASE gesmed;
      CREATE DATABASE gesmed CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
      GRANT ALL PRIVILEGES ON gesmed.* TO 'med_admin'@'localhost';
      FLUSH PRIVILEGES;
    "
    mysql -u med_admin -p gesmed < sql/gesmed_estructura.sql

------------------------------------------------------------------------
4. CÓDIGO + ENTORNO PYTHON
------------------------------------------------------------------------
git clone <tu-repo> /opt/gesmedweb   # o rsync si no se usa git
cd /opt/gesmedweb
python3 -m venv .virtual
.virtual/bin/pip install -r requirements.txt

IMPORTANTE — permisos en /opt: crear /opt/gesmedweb normalmente requiere
sudo, lo que deja el directorio (incluido .git) con dueño root mientras
el usuario normal (p.ej. "jaime") es quien corre git/python después.
Esto causa, típicamente al hacer "git pull" más adelante:

    fatal: detected dubious ownership in repository at '/opt/gesmedweb'

La solución correcta es cambiar el dueño del directorio al usuario que
lo va a operar, NO solo silenciar el aviso de git:

    sudo chown -R <tu-usuario>:<tu-usuario> /opt/gesmedweb

Usar únicamente "git config --global --add safe.directory /opt/gesmedweb"
sin el chown solo apaga la advertencia de "dubious ownership", pero los
archivos siguen siendo de root y no escribibles por el usuario normal —
el siguiente "git pull" falla igual, con un error distinto:

    error: no se puede abrir '.git/FETCH_HEAD': Permiso denegado

Si esto ya ocurrió, aplicar el chown de arriba resuelve ambos errores
de una vez (no hace falta clonar de nuevo).

------------------------------------------------------------------------
5. VARIABLES DE ENTORNO (.env)
------------------------------------------------------------------------
Generar la clave maestra de cifrado:

    python3 -c "import secrets; print(secrets.token_hex(32))"

Crear el archivo .env en la raíz del proyecto:

    GESMED_MASTER_KEY=<el hex generado arriba>
    GESMED_DB_URL=mysql+pymysql://med_admin:<password>@localhost:3306/gesmed

    # Variables sueltas, además de GESMED_DB_URL: migrations/parametros_fijos.py
    # y migrations/orquestador.py NO leen GESMED_DB_URL — arman los comandos
    # mysqldump/mysql con estas variables por separado. Si se omiten, caen a
    # valores por defecto (med_admin/gesmed01) que probablemente NO coincidan
    # con la contraseña real del servidor nuevo, y fallan con "Access denied".
    GESMED_DB_HOST=localhost
    GESMED_DB_PORT=3306
    GESMED_DB_USER=med_admin
    GESMED_DB_PASSWORD=<la misma password de arriba>
    GESMED_DB_NAME=gesmed

(GEODATA_DB_URL ya no es necesaria — se puede omitir del .env.)

NOTA sobre carga de .env: todos los scripts en migrations/ (parametros_
fijos.py, orquestador.py, crear_admin_inicial.py, verificar_estructura.py,
upsert_medicamento_presentacion.py) cargan el .env automáticamente con
python-dotenv (load_dotenv), así que ejecutarlos con
"python -m migrations.<script>" SÍ lee las variables definidas arriba.
requirements.txt ya incluye python-dotenv — no hace falta instalarlo
aparte, solo asegurarse de correr "pip install -r requirements.txt"
(paso 4) antes de estos scripts.

CRÍTICO: si este servidor va a recibir datos migrados desde amaymed
(paciente, diagnostico, prescripcion — todos con campos cifrados
AES-256-GCM), GESMED_MASTER_KEY debe ser EXACTAMENTE la misma que se
usó para cifrar esos datos originalmente. Si es una instalación 100%
nueva sin datos heredados, puede generarse una clave nueva como arriba.

6. CATÁLOGOS Y USUARIO ADMIN INICIAL
------------------------------------------------------------------------
.virtual/bin/python -m migrations.parametros_fijos --instalar

.virtual/bin/python -m migrations.crear_admin_inicial \
    --usuario admin --nombre "Administrador" --email admin@dominio.com

(pedirá la contraseña por prompt oculto, nunca como argumento en texto
plano)

------------------------------------------------------------------------
7. VERIFICACIÓN DE ESTRUCTURA (recomendado)
------------------------------------------------------------------------
.virtual/bin/python -m migrations.verificar_estructura

Confirma que el dump de estructura aplicado coincide con lo que
mis_modelos.py espera, antes de arrancar la app en producción.

------------------------------------------------------------------------
8. MIGRACIÓN DE DATOS DESDE AMAYMED (solo si se restituye desde amaymed)
------------------------------------------------------------------------
Este paso NO aplica a una instalación 100% nueva sin datos heredados —
sáltalo si no hay una base amaymed de origen. Aplica cuando el servidor
nuevo debe quedar con los datos clínicos migrados desde amaymed
(paciente, diagnóstico, atención, prescripción, exámenes, etc.).

8.1 Prerrequisito: GESMED_MASTER_KEY debe ser la misma que se usó para
    cifrar los datos migrados originalmente (ver sección 5, punto
    CRÍTICO) — si es distinta, los campos AES-256-GCM quedan
    ilegibles/corruptos tras la migración.

8.2 Restituir (o dejar accesible) la base amaymed de origen en el
    servidor nuevo, y agregar sus credenciales al .env. Hacen falta DOS
    formatos, porque el código los usa para cosas distintas — no basta
    con poner uno solo:

    AMAYMED_DB_URL=mysql+pymysql://med_admin:<password>@localhost:3306/amaymed
    AMAYMED_DB_HOST=localhost
    AMAYMED_DB_PORT=3306
    AMAYMED_DB_USER=med_admin
    AMAYMED_DB_PASSWORD=<password>
    AMAYMED_DB_NAME=amaymed

    - AMAYMED_DB_URL la usan migrations/migrador_base.py y
      migrations/migrador_medicos.py (todas las conexiones SQLAlchemy a
      amaymed) — si falta, caen a un default con password "gesmed01"
      que casi seguro NO es el tuyo, y falla con "Access denied for
      user 'med_admin'@'localhost'".
    - AMAYMED_DB_HOST/PORT/USER/PASSWORD/NAME los usa solo
      migrations/orquestador.py para armar el comando mysqldump del
      backup automático (no puede reutilizar la URL directamente ahí).

    Ambos apuntan a las mismas credenciales — no hace falta que
    coincidan literalmente en formato, pero sí en host/usuario/
    password/base. Todas tienen fallback a defaults si no se declaran,
    pero declararlas explícitamente evita este error.

8.3 Migrar primero las cuentas de los médicos (amaymed.medico → gesmed.
    points). Esto es obligatorio ANTES del orquestador: si amaymed tiene
    más de un médico registrado y solo existe la cuenta ADMIN (creada
    por crear_admin_inicial.py, que no es un médico), el orquestador no
    tiene con qué atribuir correctamente atencion/diagnostico a cada
    médico real.

    .virtual/bin/python -m migrations.migrador_medicos

    Qué hace (ver migrations/migrador_medicos.py):
      - Crea una fila en gesmed.points por cada médico de amaymed.medico
        que no exista ya (comparando por `usuario`); es idempotente, se
        puede volver a correr sin duplicar.
      - amaymed.medico no tiene id numérico (su PK es el nombre en
        texto), así que cada médico migrado recibe un id_medico NUEVO
        por AUTO_INCREMENT — no existe un id original que "conservar".
      - La contraseña de amaymed es texto plano y nunca se reutiliza: se
        genera una contraseña temporal aleatoria por médico, se guarda
        hasheada con bcrypt, y se imprime UNA SOLA VEZ en pantalla (no
        queda en ningún archivo ni log) para entregarla por un canal
        seguro y pedir el cambio en el primer ingreso.
      - Anotar los id_medico impresos al final — sirven para verificar
        la atribución de datos migrados en el paso 8.4.

8.4 Ejecutar el orquestador de migración de datos clínicos:

    .virtual/bin/python -m migrations.orquestador --medico-id <id>

    IMPORTANTE — esto migra TODOS los pacientes y TODOS los médicos de
    amaymed en una sola pasada, no es "uno por médico": el orquestador
    trunca y reconstruye las tablas destino completas en cada corrida
    (ver migrations/orquestador.py), así que NO debe repetirse una vez
    por médico — se corre una sola vez.

    El <id> de --medico-id ya NO significa "el médico de toda la
    tanda": es solo el ID de RESPALDO (fallback) que se usa para las
    pocas atenciones/diagnósticos cuyo médico en amaymed no se pudo
    reconocer por nombre contra gesmed.points (por ejemplo, un nombre
    escrito distinto entre medico_atiende y medico.nombre_medico). Debe
    ser un id_medico que YA exista en gesmed.points — usar uno de los
    creados en el paso 8.3. Si no existe, el orquestador se detiene
    antes de tocar nada y lo indica explícitamente.

    Esto hace, en un solo proceso (ver migrations/orquestador.py):
      1. Backup automático de amaymed y gesmed antes de tocar nada
      2. Verifica que el medico_id de respaldo exista en gesmed.points
      3. Aplica los ALTER TABLE necesarios (columnas a BLOB para cifrado)
      4. Trunca las tablas destino en gesmed (orden inverso de FK)
      5. Migra tabla por tabla en orden de dependencias FK, resolviendo
         lk_medico en atencion/diagnostico por nombre contra los
         médicos ya migrados en 8.3 (cae al id de respaldo solo si no
         hay coincidencia):
         paciente → diagnostico → atencion → rel_atencion_diagnostico →
         prescripcion → prescripcion_cuidados → certificado →
         examenes_grupo → examenes_catalogo → examenes_pedido →
         pedido_imagen
      6. Verifica conteos origen vs destino por tabla
      7. Reporte final; si algo falla, no continúa a ciegas

    IMPORTANTE sobre errores por registro (FK huérfana, fecha inválida,
    referencia sin resolver, etc.): el orquestador YA NO hace rollback
    completo de gesmed cuando aparecen — solo hace rollback (restaura el
    backup de gesmed tomado en el paso 1) ante un fallo CRÍTICO real
    (excepción no controlada, típicamente un problema de conexión o de
    esquema). Antes, un solo error puntual en cualquiera de las 11 tablas
    (por ejemplo, una prescripción con lk_generico apuntando a un código
    que no existe en el catálogo fijo de medicamentos) disparaba un
    rollback de TODA la base, borrando también las tablas que habían
    migrado el 100% de sus registros sin errores. Ahora esas tablas
    "buenas" quedan en gesmed aunque otras tengan errores puntuales; el
    reporte final lista cada error con su id para revisarlo/corregirlo
    a mano si hace falta. También se corrigieron dos causas concretas de
    errores puntuales que aparecían en la práctica: lk_generico/
    lk_presentacion huérfanos en prescripcion (ahora caen a NULL en vez
    de violar la FK), fechas legado "0000-00-00" en certificado (ahora
    caen a la fecha del certificado en vez de tirar ValueError), y
    pedidos de imagen sin CIE10 asociado en pedido_imagen (amaymed no
    garantizaba ese vínculo — 728 de 2192 pedidos no tenían ninguno; ahora
    el migrador cae al diagnóstico más reciente del mismo paciente en vez
    de descartar la fila, porque gesmed.examen_pedido.lk_diagnostico es
    NOT NULL — decisión de negocio confirmada con el usuario, no una
    corrección "neutra": el diagnóstico vinculado puede no ser exacto).

8.5 Upsert de tablas no cubiertas por el orquestador (si aplica):

    .virtual/bin/python -m migrations.upsert_medicamento_presentacion

    (gesmed.presentacion_medicamentos → gesmed.medicamento_presentacion,
    upsert por id_presentacion — ver el docstring del script antes de
    correrlo, sobrescribe destino por id)

8.6 Revisar el reporte final del orquestador (conteos origen/destino
    por tabla) y los errores impresos por consola antes de dar la
    migración por buena. Prestar atención especial a las advertencias
    "sin medico_atiende/medico_diagnostica reconocido" — indican
    registros que cayeron al médico de respaldo y conviene revisar
    manualmente cuál era el médico correcto.

------------------------------------------------------------------------
9. LEVANTAR LA APP
------------------------------------------------------------------------
reflex init      # primera vez: descarga bun, instala deps del frontend
reflex run --env prod

Nota sobre componente de calendario: .web/ está en .gitignore (es el
build generado por Reflex), pero el calendario usa un componente JSX
escrito a mano (.web/calendario_medico.jsx) que por eso nunca viajaba
con git clone — causaba "Could not load calendario_medico ... No such
file or directory" al hacer build en un servidor nuevo. Ya se resolvió:
rxconfig.py ahora copia automáticamente GesmedWeb/custom_components/
*.jsx hacia .web/ cada vez que se corre cualquier comando reflex (init,
run, export), siempre que .web/ ya exista. No requiere ningún paso
manual adicional, pero si en el futuro se agrega otro componente JSX
escrito a mano, debe guardarse en GesmedWeb/custom_components/ (no
solo en .web/) para que sobreviva un clon nuevo del repo.

Nota sobre paquetes npm de FullCalendar: por la misma razón (.web/
regenerado desde cero no conserva nada instalado a mano con
"bun add"), el build de producción podía fallar en un servidor/clon
nuevo con:

    [plugin:vite:import-analysis] Failed to resolve import
    "@fullcalendar/react" from "calendario_medico.jsx"

Ya se resolvió: rxconfig.py corre automáticamente "bun add" para los
paquetes @fullcalendar/{react,daygrid,timegrid,interaction,core}, fijos
en la versión 6.1.21 para los 5 (ver _instalar_paquetes_npm_custom en
rxconfig.py), la primera vez que corre cualquier comando reflex con
.web/ ya creado y sin @fullcalendar/react instalado todavía. IMPORTANTE:
no declarar estos paquetes en "lib_dependencies" del componente
CalendarioMedico (GesmedWeb/componentes/calendario_fc.py) — reflex sí
lo procesa, pero instala la ÚLTIMA versión de cada paquete sin respetar
compatibilidad entre ellos: resuelve @fullcalendar/core y
@fullcalendar/react a v7.x (que ya no expone
"@fullcalendar/core/locales/*" ni "/internal.js" como antes) mientras
daygrid/timegrid/interaction quedan en v6.x, una combinación
incompatible que rompe el build con errores de resolución de imports.
Si algún día hace falta subir de versión, hay que fijar los 5 paquetes
a la MISMA versión nueva a la vez en _PAQUETES_NPM_CUSTOM (rxconfig.py)
y probar un build de producción completo antes de dar por buena la
actualización.

Para producción real (proceso persistente + reverse proxy), lo habitual
es agregar sobre esto:
  - reflex export (build de frontend + backend para producción)
  - un servicio systemd para mantener el proceso corriendo
  - nginx como reverse proxy (TLS, dominio, etc.)
Esto no está incluido en esta guía — pedirlo aparte si se necesita.

------------------------------------------------------------------------
10. ACCESO REMOTO VÍA VPN (WireGuard)
------------------------------------------------------------------------
Objetivo: nadie accede a GesmedWeb ni a MariaDB directamente por
internet. Solo se expone el puerto de WireGuard (UDP); la app y la BD
quedan escuchando únicamente en la IP privada de la VPN.

10.1 Instalar WireGuard en el servidor

    sudo apt install -y wireguard

10.2 Generar claves del servidor

    wg genkey | sudo tee /etc/wireguard/server_private.key
    sudo chmod 600 /etc/wireguard/server_private.key
    sudo cat /etc/wireguard/server_private.key | wg pubkey | \
      sudo tee /etc/wireguard/server_public.key

10.3 Configurar la interfaz del servidor

    sudo nano /etc/wireguard/wg0.conf

    [Interface]
    Address = 10.10.0.1/24
    ListenPort = 51820
    PrivateKey = <contenido de server_private.key>
    # Habilita forwarding/NAT solo si el cliente necesita salir a
    # internet a través del servidor; para acceso solo a GesmedWeb no
    # hace falta.

    [Peer]
    # Un bloque [Peer] por cada equipo cliente que se conecte
    PublicKey = <clave pública del cliente>
    AllowedIPs = 10.10.0.2/32

10.4 Levantar la interfaz y habilitarla al boot

    sudo systemctl enable --now wg-quick@wg0
    sudo wg show

10.5 Abrir el puerto en el firewall (ufw)

    sudo ufw allow 51820/udp
    sudo ufw allow OpenSSH
    sudo ufw enable

    IMPORTANTE: no abrir los puertos de Reflex (3000/8000) ni de
    MariaDB (3306) al exterior — solo deben ser alcanzables dentro de
    la VPN (ver 9.7).

10.6 Configurar el cliente (equipo remoto)

En el equipo desde el que se accederá remotamente:

    sudo apt install -y wireguard   # o WireGuard app en Windows/macOS
    wg genkey | tee client_private.key | wg pubkey > client_public.key

    sudo nano /etc/wireguard/wg0.conf

    [Interface]
    Address = 10.10.0.2/24
    PrivateKey = <contenido de client_private.key>

    [Peer]
    PublicKey = <server_public.key del servidor>
    Endpoint = <IP-pública-del-servidor>:51820
    AllowedIPs = 10.10.0.1/32   # solo tráfico hacia el servidor gesmed
    PersistentKeepalive = 25

    sudo wg-quick up wg0

Copiar la clave pública del cliente (client_public.key) al bloque
[Peer] del servidor (paso 9.3) antes de conectar.

10.7 Restringir MariaDB a la VPN (no exponerla a la red pública)

    sudo nano /etc/mysql/mariadb.conf.d/50-server.cnf
        bind-address = 10.10.0.1     # solo la IP de la VPN, no 0.0.0.0

    sudo systemctl restart mariadb

Y el GESMED_DB_URL en .env sigue apuntando a localhost/127.0.0.1 en el
propio servidor (la app y la BD corren en la misma máquina) — el
bind-address solo importa si algún día separas la BD a otro host
dentro de la VPN.

10.8 Probar la conexión

Desde el equipo cliente, con la VPN levantada:

    ping 10.10.0.1
    ssh usuario@10.10.0.1        # si SSH también se restringe a la VPN
    curl http://10.10.0.1:3000   # si reflex run expone ahí el frontend

Si reflex run escucha en 0.0.0.0 por defecto, ya es alcanzable desde
10.10.0.2 sin abrir ningún puerto adicional al público — el único
punto de entrada expuesto a internet es el puerto UDP de WireGuard.

10.9 Checklist rápido para mañana
    [ ] wireguard instalado en servidor y equipo cliente
    [ ] claves generadas en ambos lados
    [ ] wg0.conf servidor con [Peer] del cliente
    [ ] wg0.conf cliente con Endpoint = IP pública del servidor
    [ ] ufw: solo 51820/udp y SSH abiertos al público
    [ ] mariadb bind-address restringido a la IP de la VPN
    [ ] ping + curl exitoso entre cliente y servidor por la VPN

========================================================================
RESUMEN DE ORDEN DE EJECUCIÓN
========================================================================
1. apt install (sistema + mariadb + node)
2. crear BD gesmed + usuario med_admin
3. mysql gesmed < gesmed_estructura.sql
   (generado con mysqldump real, excluyendo vistas *_amaymed*)
4. git clone + venv + pip install -r requirements.txt
   (si /opt requiere sudo: sudo chown -R <usuario>:<usuario> /opt/gesmedweb)
5. crear .env (GESMED_MASTER_KEY, GESMED_DB_URL)
6. python -m migrations.parametros_fijos --instalar
7. python -m migrations.crear_admin_inicial --usuario ...
8. python -m migrations.verificar_estructura   (opcional, para confirmar)
9. [solo si se restituye desde amaymed]
   9a. python -m migrations.migrador_medicos   (médicos → gesmed.points,
       correr UNA vez, obligatorio antes del orquestador si hay más de
       un médico real en amaymed)
   9b. python -m migrations.orquestador --medico-id <id-de-respaldo>
       (correr UNA vez, no por médico — <id> es solo el fallback para
